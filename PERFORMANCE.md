# Matting Performance — Phase 14 Audit & Benchmarks

Scope: the background-removal / matting system covered in `MATTE_IMPLEMENTATION_PLAN.md`, as shipped through Phase 13. This phase's brief: ensure correctness first, then optimize against a specific 14-item checklist, without reducing quality to hit an arbitrary FPS target, and build real benchmarks.

Every claim below was verified by reading the actual code or by running the benchmark tool live (`/tools/video/remove-background-benchmark`) — nothing here is guessed.

## How to run the benchmark

Visit `/tools/video/remove-background-benchmark` (not linked from the main site — an internal diagnostic tool, same pattern as this file) and click "Run benchmark". It runs the real production pipeline (`src/lib/matting/pipeline/remove-background.ts`) against synthetic images at three resolutions, plus three simulated video cases (sparse-sampled frames at a given fps), and reports per case: model used, inference time, total time, JS-heap memory delta, and throughput. "Copy as Markdown" exports the results. See `src/lib/matting/benchmark.ts` for the implementation and its documented limitations (notably: no browser API exposes GPU memory to page JS, so that column is always `n/a` — never fabricated).

## The 14-item checklist

1. **Model caching** — already correct before this phase. `getSharedModelRegistry()` (`src/lib/matting/models/registry.ts`) is a process-lifetime singleton; every adapter's `load()` is idempotent (checks `isLoaded()` first). Downloaded model *bytes* are also cached across page loads via Cache Storage (`src/lib/ml/model-cache.ts`). Verified in the benchmark's own data: `image-480p`'s inference time (905ms, cold) vs. `image-1080p`'s (388ms, warm) on the same run.
2. **GPU memory reuse** — already correct: sessions are never recreated per inference call (see #1), so onnxruntime-web's own WebGPU buffer pool is reused automatically. No further user-facing API exists in onnxruntime-web to tune this beyond "don't create a new session per call," which was already true.
3. **Batch processing where appropriate** — the appropriate strategy here is *sparse frame sampling* (already implemented, `person-cutout.ts`'s `pickCutoutSampleFps`/`maxSafeCutoutInputs`), not literal tensor batching. Stacking frames into a batch-dim>1 tensor would require every adapter's graph to support it (unverified — u2net's bundled export may well be fixed at batch=1) and offers no clear win when only ~6-12 frames are ever sampled per clip. Not attempted — this is exactly the kind of premature, unverified optimization the phase brief warns against.
4. **Tensor precision where safe** — `RuntimeDevice.useFp16` is already detected (`onnx-runtime.ts`, via `adapter.features.has("shader-f16")`) but no bundled model currently ships an fp16 ONNX export, so there is nothing to switch to without fetching new weight files — out of this phase's scope. Documented rather than faked.
5. **ONNX/TensorRT acceleration where compatible** — ONNX Runtime Web (wasm/WebGPU execution providers) is already the app's inference engine. TensorRT is not available in a browser sandbox at all (it's a native/server-side runtime) — not applicable here, not a gap.
6. **Hardware decoding** — video frame sampling already uses the browser's own native `<video>` element (`video.currentTime` seeks, hardware-accelerated where the platform supports it) rather than software-decoding through ffmpeg.wasm — already the right choice, made in earlier phases.
7. **Hardware encoding** — ffmpeg.wasm's encoders (`libx264`, `prores_ks`) are software-only; no ffmpeg.wasm build exposes hardware encode. A WebCodecs-based alternative encode path is a substantial architecture change (a second export pipeline bypassing ffmpeg) — out of scope for this phase; noted as a real future option, not attempted without evidence it's needed.
8. **Streaming** — already correct: video is processed frame-by-frame via seek+draw, never loaded wholesale into memory.
9. **Frame pipelining** *(changed this phase)* — `sampleTrimmedFrames` (`src/lib/captions/person-cutout.ts`) now overlaps frame *i+1*'s seek+draw with frame *i*'s model inference, instead of doing them fully sequentially. Each frame gets its own freshly-allocated canvas specifically so this overlap can never race with or corrupt an in-flight inference call.
10. **CPU/GPU overlap** *(changed this phase)* — a direct consequence of #9: video decode (GPU/media-decode hardware) now runs concurrently with matting inference (CPU/GPU compute) instead of one blocking the other.
11. **Worker queues** — already correct: WASM inference is proxied to a worker (`ort.env.wasm.proxy = true` for the wasm provider), and ffmpeg.wasm already runs in its own worker.
12. **Progress reporting** — already extensive throughout the pipeline (engine-load/run progress, per-frame progress, matte-generation progress from Phases 12-13).
13. **Cancellation** *(added this phase — was a real, confirmed gap)* — `runFfmpeg` now accepts an `AbortSignal` (`FfmpegCancelledError` on abort), wired into `useFfmpegExport`/`useBgRemovalExport`'s video export paths. `sampleTrimmedFrames` also accepts a `signal`, checked between frames — genuinely effective (stops scheduling new work; can't interrupt an in-flight model call, since onnxruntime-web's `session.run()` has no cancellation API). Both wired into `RemoveBackgroundTool.tsx`'s UI ("Detect subject" and "Remove background" both grow a Cancel button while running). Verified live: video-export cancellation settles in ~1-2 polling ticks; cutout-generation cancellation settles within one frame's remaining processing time (the theoretical minimum for cooperative, non-preemptive cancellation).
14. **Memory cleanup** *(fixed this phase — a real bug)* — every ONNX-session-holding adapter's `unload()` (`u2net.ts`, `modnet.ts`, `background-matting-v2.ts`) previously just dropped its `session` reference without calling `session.release()`, leaking the underlying WASM heap allocation / GPU buffers if `unload()` were ever invoked. Fixed via a new shared `releaseInferenceSession()` helper (`src/lib/ml/onnx-runtime.ts`). Object-URL cleanup (`revokeObjectURL` on reset/regenerate) was already correct throughout. Note: `unload()` itself is not currently called anywhere in the app — this is a traditional multi-page Astro app (no client-side router), so a full page navigation already frees everything; the fix matters for correctness if/when something does call it, not as an active leak today.

## What was NOT done, and why

- No forced WebGPU-vs-WASM micro-benchmark: u2net (the one reliably-bundled, working model) is deliberately pinned to WASM due to a confirmed onnxruntime-web WebGPU incompatibility (`u2net.ts`'s own doc comment). Forcing it onto WebGPU anyway just to produce a comparison number would mean benchmarking a code path production never takes.
- No tensor batching, no fp16 casting, no new hardware-encode pipeline — see items 3/4/7 above. Each would be genuine, unverified, invasive surgery on inference-critical code for a checklist item alone, which the phase's own "do not optimize prematurely" instruction explicitly rules out absent a measured need.
