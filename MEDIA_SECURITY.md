# Media Security — Phase 17 Audit & Data Lifecycle

Scope: the background-removal / matting system covered in `MATTE_IMPLEMENTATION_PLAN.md`, as shipped through Phase 16, plus the shared client-side infrastructure it depends on (ffmpeg.wasm, onnxruntime-web, model cache). This phase's brief: audit every place user media touches storage/logs/workers, and fix real gaps — not a theoretical checklist pass.

Every claim below was verified by reading the actual code (file/line references throughout) — nothing here is guessed.

## The architecture that makes most of this checklist trivially true

Clipbench is a client-side-only app: uploaded images/video are never sent to any server. There is exactly one server-side route in the whole app (`src/pages/api/transcribe-source.ts`, the Video Transcript tool's yt-dlp backend) and it never touches matting media — the matting/bg-removal tool has **zero network calls involving user media**, ever. This single fact satisfies requirement #1 ("do not expose uploaded media publicly") by construction: there is no server to expose it from, and blob: object URLs (the only "URLs" user media ever gets) are tab-local and unreachable from any other origin or page.

## Audit findings, by requirement

1. **Do not expose uploaded media publicly.** Satisfied architecturally (see above). Confirmed no `fetch`/`XMLHttpRequest` call anywhere under `src/lib/matting/`, `src/lib/media/`, or the bg-removal hooks ever includes user file bytes — the only outbound network calls in that whole area are `model-cache.ts`'s model-weight downloads (Hugging Face / same-origin, public model files, not user data).

2. **Do not log raw image/video content.** Audited every `logger.*`/`console.*` call reachable from the matting pipeline (`pipeline/remove-background.ts`, `model-router.ts`, `router.ts`, all `useBgRemovalExport.ts`/benchmark panels). Every logged `data` payload is structured metadata only — dimensions, model IDs, difficulty/confidence scores, boolean indicators (`RoutingRequest`'s fields) — never a pixel buffer, `ImageData`, `File`, or `Blob`. No violation found.

3. **Do not log sensitive metadata unnecessarily.** Same audit as #2. The one server route (`transcribe-source.ts`) logs only the error message on failure (`console.error("[api/transcribe-source] yt-dlp failed:", message)`) — never the submitted URL or downloaded content. No violation found.

4. **Clean temporary files.** ffmpeg.wasm's virtual filesystem: `runFfmpeg` (`src/lib/ffmpeg/engine.ts`) deletes every written input and the output file in a `finally` block, on both success and failure/cancellation paths — confirmed already correct (predates this phase). The one real server-side temp dir (`transcribe-source.ts`'s per-request `mkdtemp` under `os.tmpdir()`) is removed in a `finally` block (`rm(dir, { recursive: true, force: true })`) regardless of outcome. Object URLs (`URL.createObjectURL`) are revoked on reset/re-pick (`RemoveBackgroundTool.tsx`, `useBgRemovalExport.ts`) — not on component unmount, but blob URLs are tab-scoped and released by the browser when the document is torn down regardless, so this isn't a persistence or exposure concern, just an accepted minor memory-hygiene tradeoff.

5. **Prevent path traversal.** No user-controlled string is ever used as a filesystem or virtual-FS path. ffmpeg virtual-FS filenames are always app-generated constants (`input.${ext}`/`output.${ext}`), where `ext` comes from `guessVideoExtension`/`guessImageExtension` (`src/lib/ffmpeg/format.ts`) — an **allowlist lookup** against a fixed small map, not a pass-through of the original filename (confirmed: a crafted filename like `a.mp4; ../../etc` fails the map lookup and falls back to MIME-sniffing, then to a safe default). The server route resolves its output file by listing `readdir(dir)` inside its own freshly-created temp dir, never by joining a user-supplied path.

6. **Validate file types.** Was a real gap for the matting tool: `handleFiles` in `RemoveBackgroundTool.tsx` decided image-vs-video from `file.type` alone and otherwise relied entirely on the decoder's own `onerror` (Phase 16's `handleImageError`/`handleVideoError`) to reject a bad file — correct (never a fake success) but late, and had no explicit type allowlist. **Fixed:** new `validateUploadedMediaFile()` (`src/lib/media/upload-validation.ts`) runs before a file is touched at all — accepts by MIME type (`image/*`/`video/*`), falls back to the same extension-allowlist approach as `format.ts` when the browser reports no MIME type, and rejects anything else with a clear message. The decoder-level `onerror` handlers remain as the second line of defense for files that pass this check but are still corrupt/truncated.

7. **Validate file size.** Was a real, confirmed gap: no size check existed anywhere on the upload path (Phase 16's `MAX_PIXELS` ceiling only catches oversized *decoded dimensions*, after a file has already been fully loaded into memory). **Fixed:** `validateUploadedMediaFile()` rejects images over 150MB and video over 2GB before creating an object URL or attempting to decode. Limits were chosen against real numbers already established in this project: 150MB comfortably exceeds a 24MP (this app's own `MAX_PIXELS`) uncompressed RGBA frame (~96MB decoded); 2GB is a safety ceiling against exhausting ffmpeg.wasm's wasm heap, which loads a file wholesale into its virtual FS. The one server route already had an equivalent limit (`--max-filesize 300M` passed to yt-dlp) from when it was built.

8. **Prevent malicious media payloads where possible.** This app never hand-parses untrusted image/video bytes — every user-supplied file is decoded exclusively through the browser's own sandboxed native decoders (`<img>`, `<video>`, `createImageBitmap`) or ffmpeg.wasm's own WASM sandbox; there is no custom native parser in the line of fire of arbitrary user input. The one hand-rolled binary parser in the codebase, `decodeTiffToRgba` (`src/lib/media/tiff-encoder.ts`), is bounds-checked at every offset read (IFD entry count, strip offset + length all checked against `buffer.byteLength` before any allocation or read) and — critically — is only ever invoked on this app's own freshly-generated export blob (`export-validation.ts`, verifying our own output), never on an arbitrary uploaded file. No changes needed; audited and confirmed sound.

9. **Isolate ML workers appropriately.** WASM inference already runs proxied to a dedicated Web Worker (`ort.env.wasm.proxy = true` for the wasm provider, `src/lib/ml/onnx-runtime.ts`), and ffmpeg.wasm runs its own worker (`ffmpeg-core.worker.js`, same-origin, self-hosted under `/ffmpeg`) — both get the browser's standard worker isolation (separate global scope, no DOM access). One accepted tradeoff, not a gap introduced by this phase: onnxruntime-web's own WASM/worker loader script is fetched from jsdelivr (a CDN) rather than self-hosted, because self-hosting it hit a Vite dev-server restriction (documented in `onnx-runtime.ts`'s own comment) — this is a supply-chain consideration worth knowing about, not something changed here, since the same tradeoff already existed for this app's Whisper/Kokoro model downloads.

10. **Ensure failed jobs clean up resources.** Confirmed via the `finally` blocks already covered under #4: `runFfmpeg` always deletes its virtual-FS files regardless of success/failure/cancellation; the transcript route always removes its temp dir regardless of outcome; Phase 14 already made cancellation cooperative and resource-safe. No new gap found.

## What changed this phase

- **New:** `src/lib/media/upload-validation.ts` + test — `validateUploadedMediaFile()`, the file-type and file-size gate described under #6/#7.
- **Changed:** `RemoveBackgroundTool.tsx`'s `handleFiles` now validates before doing anything else with a picked file, instead of only discovering a bad file via a decode error later.

## Data lifecycle (uploaded file → export)

1. **Upload** — user picks/drops a file (`Dropzone.tsx`). `validateUploadedMediaFile()` gates type + size immediately; a rejected file is never turned into an object URL or touched by any decoder.
2. **In-memory decode** — an accepted file becomes a tab-local `blob:` object URL, decoded by the browser's native `<img>`/`<video>` element. Nothing leaves the device; nothing is written to disk.
3. **Inference** — pixel data is read into an `ImageData`/canvas buffer and handed to the selected matting model (ONNX Runtime Web), running in-process (WASM worker or WebGPU) on the same device. Model *weights* (not user data) may be fetched from Hugging Face/same-origin and cached in browser Cache Storage (`clipbench-ml-models-v1`) — confirmed that cache is keyed only by model download URLs, never by anything derived from user files.
4. **Refinement/export** — the resulting alpha/matte is composited client-side; video export additionally round-trips through ffmpeg.wasm's virtual filesystem, which is scoped to a single call and deleted in a `finally` block whether the call succeeds, fails, or is cancelled.
5. **Result** — the export is handed back as a `Blob` + tab-local object URL for preview/download. Revoked on reset/re-pick; released by the browser regardless once the tab/document is closed.
6. **Nothing persists** across page loads except: the user's theme preference (`localStorage["theme"]`) and, only on the internal, unlisted quality-benchmark tool, synthetic benchmark reports/ratings (`localStorage` keys under `clipbench:matte-quality-*`) — never real uploaded media.

## What was NOT done, and why

- No change to Object-URL revocation-on-unmount: blob URLs are tab-scoped, unreachable cross-origin, and freed by the browser when the document is destroyed — treating this as a security gap would be fixing a property that was never true (public exposure), not a real one.
- No change to onnxruntime-web's CDN-hosted WASM loader: an existing, documented, pre-Phase-17 tradeoff forced by a Vite dev-server restriction, not something introduced or newly discovered this phase.
- No broader sweep of the other ~25 non-matting tools: they share the same underlying `runFfmpeg`/temp-file-cleanup infrastructure already audited under #4/#10, but re-auditing every tool's own upload screen for the same type/size gate is a straightforward follow-up, not attempted here to stay in scope with this project's established per-feature phasing.
